# Processing machines

| Machine | Built as | Inputs / outputs | Processing |
| --- | --- | --- | --- |
| Electric Arc Furnace | Java, MMDLib `BaseMachine` | 4 parallel item inputs / 6 outputs | Current smelting recipes; 200 ticks and 8 FE per tick per active lane |
| Electric Rock Crusher | Java, MMDLib `BaseMachine` | 3 parallel item inputs / 6 outputs | MMDLib crushing recipes; 200 ticks and 12 FE per tick per active lane |
| Electric Oven | MMDLib XML machine | 1 item input / 1 output | Smelting recipes whose result is food; 100 ticks at 4 FE per tick |
| Electric Still | MMDLib XML machine | 1 input tank / 1 output tank, 1,000 mB each | Power Advantage distilling recipes; recipe time at 16 FE per tick |
| Petro-Plastic Refinery | MMDLib XML machine | 2,000 mB oil tank / 1 item output | 100 mB crude or refined oil makes one ingot; 100 ticks at 12 FE per tick |

All five hold 500 FE and accept up to 4,096 FE per tick, through the electric cable network or any
other FE source.

## Oven, still and refinery: MMDLib XML machines

These three are declared in `src/main/resources/mmdlib/machine/*.xml`. MMDLib registers their
blocks, items, block entities, recipe types, capabilities, screens and JEI categories; EA3 has no
Java class for them. Each extends MMDLib's `base_powered_machine`, so its screen is MMDLib's standard
machine screen: the slots and tanks, a progress arrow, a power gauge, and drawers for information,
side configuration (with automation addons) and redstone.

**Recipes.** Each declares its own MMDLib machine recipe type:

- `electricadvantage:oven_cooking`: generated by `processing.FoodSmeltingRecipes` from every smelting
  recipe whose result is food, at a fixed 100 ticks and 4 FE per tick. Datapack smelting recipes are
  picked up on reload.
- `electricadvantage:electric_distilling`: generated by `processing.ElectricDistillingRecipes`, a copy of
  every Power Advantage `poweradvantage:distilling` recipe with 16 FE per tick added. Adding or
  removing Power Advantage distilling recipes (datapacks, CraftTweaker, KubeJS) changes the still too.
  Only fluid-to-fluid recipes using Power Advantage's `input` and `output` groups are copied.
- `electricadvantage:plastic_refining`: authored in
  `data/electricadvantage/recipe/plastic_refining.json`: 100 mB of `#poweradvantage:crude_oils` or
  `poweradvantage:refined_oil`, 1,200 FE, 100 ticks, one petro-plastic ingot. Packs can add or replace
  these like any machine recipe.

Recipes are MMDLib machine recipes, so `/reload` rebuilds them and CraftTweaker can edit them with
`<recipetype:electricadvantage:...>` or `mods.mmdlib.MachineRecipeBuilder`.

**Moving items and fluids.** These machines no longer push their outputs into neighbours on their
own. Install an addon in the group's addon slots, in the side configuration drawer:

- Electric Advantage's **Item Output Port** pushes an item group into neighbouring inventories and the
  **Item Intake Port** pulls items in, 16 items per tick, with no power cost. They work in any MMDLib
  machine. See `automation/ItemPorts`.
- Power Advantage's **Fluid Intake Pump** and **Fluid Output Pump** do the same for tanks, as for Power
  Advantage's own Distillery.

Without addons, hoppers, pipes and other mods can still insert into inputs and extract from outputs,
on the faces the side configuration allows.

**Appearance.** Each uses the shared casing model `block/electric_machine_casing` (no front face) and
three front parts chosen by MMDLib conditions: `_front_on` while the processor is running,
`_front_powered` while it holds enough energy for one tick, `_front_off` otherwise. The item models
still show the full `_off` block.

**Redstone.** A redstone signal no longer stops these three by itself. Each face can be set to read
redstone in the redstone drawer; MMDLib XML machines ignore redstone by default.

**Worlds from 3.0.** The XML storage keeps 3.0's save keys, so the oven's items, the refinery's
plastic and oil, and the still's input oil load into the new machines. Lost on upgrade: buffered
energy, progress in a cycle, and the still's output tank (3.0 saved it separately, under `Output`).
The machines' hardness is now 3 and their blast resistance also 3 (was 10), from MMDLib's block
settings.

## Furnace and crusher: Java on MMDLib's BaseMachine

The Arc Furnace and Rock Crusher work on several inputs at once, one lane per input slot. MMDLib XML
machines have a single processor, so these stay Java, as `ProcessingBlockEntity`, built on MMDLib's
`BaseMachine`. MMDLib owns their storage persistence, client sync and dropping contents when broken;
they keep their own lanes, screens and neighbour export.

Recipe lanes keep independent progress, recipe IDs and input items, so changing an input cannot reuse
another recipe's progress. A result must fit completely across the output slots before progress
spends energy; completion inserts the full result and consumes exactly one input. Losing power
reduces a lane's progress by one tick per tick; a redstone signal pauses them. Outputs are pushed
into neighbouring inventories, up to 16 items per tick in total. Models distinguish active,
idle-but-powered and unpowered.

Saves keep 3.0's `Items`, `Progress`, `Recipe<n>` and `Work<n>` keys. The energy buffer is now saved
under MMDLib's `energy` key; 3.0's `Energy` is still read.

## Verification

```sh
./gradlew --offline build
./gradlew --offline -PgameTests runGameTestServer
python3 scripts/validate_resources.py
xvfb-run -a ./gradlew --offline -PgameTests -PclientSmoke runClient
```

`ProcessingGameTests` cover four saved/resumed smelting lanes, three crushing lanes with exact output
counts, atomic full-output behaviour, live electric supply to a furnace exporting into a chest, menus
and crafting recipes, and loading 3.0's `Energy` key.

`XmlMachineGameTests` cover the oven's food filter and 100-tick cooking, the still running a Power
Advantage distilling recipe at 16 FE per tick, the refinery with both oils and a full output, loading
3.0 saves of all three, cable power reaching an XML machine, both item ports, menus, crafting recipes
and the creative tab.

`BaseMachineGameTests` check that every Java machine reads 3.0's `Energy` key, that idle machines save
right after loading, and that broken machines drop their contents once.

The client smoke loads every model, including the XML machines' generated blockstates and parts. The
new appearance, the MMDLib screens and both kinds of addon have not yet been checked in a live client.
